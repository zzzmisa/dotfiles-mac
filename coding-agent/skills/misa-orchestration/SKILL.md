# モデルオーケストレーション

指揮役はユーザーの目的を完了まで進め、設計・統合判断に責任を持つ。
指揮役の判断力は設計・統合判断と成果物の評価に使い、独立して任せられる仕事は作業役へ渡す。
単なるファイル数やフェーズ数ではなく、独立して任せられる仕事があるかで分担を決める。
この方針はモデルやベンダーを問わず適用し、モデル固有の前提は置かない。

## 分担する条件

- 複数領域の変更で、独立した調査・実装・レビューを切り出せ、時間短縮または品質向上が
  見込める場合はサブエージェントへ委譲する。指揮役も並行して有用な作業を進める。
- 調査・テスト実行・ログ確認など、出力が大きく読み取り中心の仕事は委譲に向く。
  並列化に加えて、指揮役の文脈を要点だけに保てる。同じファイル群へ書き込む仕事の
  並列化は慎重にする。
- 小さな変更、密結合な変更、引き継ぎの説明が実作業を上回る仕事は指揮役が直接行う。
- 設計、曖昧な要件、データ互換、中核ロジックの最終判断は指揮役が持つ。
  独立した調査・設計案の検討・実装は、必要な判断力を持つ作業役へ任せてよい。
  難しい仕事を量だけで軽量モデルへ渡さない。
- 単一の探索・コマンド実行で足りる仕事にエージェントを増やさない。
  読み取りツールの並列実行で足りるなら、それを使う。

## モデルと実行手段

- このセッションに提供されているネイティブのサブエージェント機能を優先する。
  Claude Code の Agent ツール、Codex のサブエージェント（`spawn_agent` など）は、実際の
  ツール定義で利用可否・同時実行枠・文脈継承（新規文脈か会話の継承か）を確認する。
  モデル・reasoning effort の変更と文脈継承の組み合わせ制約も確認する。
  ユーザー用の新規タスク作成ツールを内部の委譲に代用しない。
- 作業役のモデルは原則として親を継承する。明確で独立した一括置換・定型更新などは、
  品質を保てる場合だけ利用可能な軽量モデルを選ぶ。難易度と判断の多さを優先する。
- 指揮役の reasoning effort は現在の設定を尊重し、必要性と選択肢を確認して変更する。
  作業役の effort は継承が既定で、定型作業は下げてよい。推奨の既定値はモデルごとに
  違うので決め打ちせず、現在の設定と提供元の案内で確認する。
- 自動委譲を含む effort（Codex の `ultra` など）が有効でも、統合と diff 確認の責任は
  指揮役に残る。自動委譲のない effort では、モデルは自発的に委譲しないことがあるため、
  分担する条件に当てはまった時点で指揮役が明示的に委譲する。
- CLI への委譲が適する場合だけ、[CLI ワーカー](references/cli-workers.md) を読む。
  ネイティブ機能が使えないだけなら、指揮役による続行も選べる。

## 任せる単位

作業役は新規の文脈で始まることが多く、会話・指揮役が読んだファイル・起動済みスキルを
持たない前提で、必要な範囲で以下を渡す。会話を継承する場合でも担当境界は明示する。

- 目的、対象ファイルや領域、受け入れ条件
- 適用するリポジトリ規約と、判断に必要な既知の事実
- 編集してよい範囲、他の担当との境界、必要な検証
- コミット禁止。push・公開・審査提出・削除などの権限は委譲によって増えない
- 戻す内容: 変更・発見の要点、検証結果、未解決事項、参照ファイル

担当は可能なら調査から実装・検証まで完結する単位にする。指揮役と作業役が同じ領域を
最初から全面調査し直す分担を避ける。判断の前提が変わったら、影響する担当へ伝える。

## 並行作業と統合

- 同じ作業ディレクトリでは編集ファイルを分離する。共有ファイルの変更は指揮役に集約するか
  直列にする。別 worktree でも共有設定・生成物・外部サービスの競合に注意する。
- 作業役はバックグラウンドで動かし、指揮役は結果に依存しない作業を先に進める。
  待つのは結果が必要になった時点にし、未完了の作業役の結果を推測して統合しない。
- 指揮役は作業役の完了報告だけで済ませず、実際の diff と必要な根拠を確認して統合する。
  実装担当は必要な検証まで行う。独立レビューを委譲する場合は、実装担当とは別の
  新しい文脈のエージェントに任せる。
- 検証は変更のリスクとリポジトリ規約に合わせる。低リスクの文言修正に新規テストを作らず、
  必要なチェックが通ったら、新しい変更・失敗・懸念がない限り繰り返さない。
- 利用上限やツール不在で委譲が失敗したら、途中の変更と実行中の作業を確認し、
  担当を回収して続行する。ユーザーの停止指示は尊重する。
- コミットは依頼範囲とリポジトリ規約に従う。必要な場合も直前に `git status` を確認し、
  ユーザーの変更と混ぜない。

## 自律性と確認

日常的な実装判断は文脈から補って進める。既に許可された作業の承認を取り直さない。
確認が必要なのは、目的や重大な結果が変わる未確定事項、または未承認の操作がある場合。
その場合も独立して進められる準備を終え、具体的な差分・選択肢を示して確認する。

分担・自律性・検証の指針は、OpenAI の
[GPT-6 ファミリー向けモデルガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)
（Astra・Sol・Luna 共通）と [Codex のサブエージェント](https://learn.chatgpt.com/docs/agent-configuration/subagents)、
Anthropic の [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)・
[Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)・
[Claude Code のサブエージェント](https://code.claude.com/docs/en/sub-agents) に合わせた（2026-09-26 確認）。
実行時にはこのスキルより上位の指示と、現在提供されているツール仕様を優先する。
