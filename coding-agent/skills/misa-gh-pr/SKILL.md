# GitHub Pull Requestの作成

## Workflow

PRを書き始める前に:

1. 対象リポジトリを特定する。
2. 対象に適用されるリポジトリの指示を読む。既に読んだ内容は再利用する。
   `AGENTS.md` と `CLAUDE.md` に加えて、
   `CONTRIBUTING.md`、`.github/pull_request_template.md`、
   `.github/PULL_REQUEST_TEMPLATE/` があればコントリビューションガイドと
   PRテンプレートも読む。
3. 優先順位は、ユーザーからの明示的な指示 → 対象リポジトリのルールとテンプレート。
   リポジトリ固有の指定は、このスキルの既定フォーマットと進め方より優先する。

リポジトリに使えるPRテンプレートがあれば、そのセクション構成と要求事項に従う。
無ければ [既定PRテンプレート](references/pull_request_template.md) を読み、Misaの既定テンプレートを使う。

### Misaの既定テンプレート

リポジトリに使えるPRテンプレートが無いときは、この順のセクションで構成する:

- `対応Issue`
- `変更内容`
- `実装理由`
- `確認したこと`
- `確認できていないこと・残る懸念点`
- `レビューしてほしいポイント`

コメントとプレースホルダは、具体的で簡潔な日本語で埋める。最終的なPR本文から
HTMLコメントは削除する。

`対応Issue` には、対応するIssue番号が分かっているときだけ `Closes #<number>` と書く。
Issue番号を推測して書かない。番号が不明なら `なし` と書き、未完成の `Closes #` を残さない。
部分対応なら `Refs #<number>` とし、完了していないIssueを自動クローズしない。

`確認したこと` は、このセッションで実際に実行・確認したものだけ `[x]` にする。
必要だが確認できていない項目は `[ ]` と理由を残す。変更に無関係な既定チェックは
削除または対象外とし、文書変更のためにアプリをビルドするなどの検証を増やさない。

`確認できていないこと・残る懸念点` と `レビューしてほしいポイント` は、
特に挙げることが無ければ `なし` と書く。

リポジトリにより具体的なルールが無い限り、進め方も次に従う:

- 作業ブランチを使う。番号付きIssueに対する作業ブランチ名は
  `issue-<number>-<short-description>` を基本に、環境で必要な接頭辞を付ける
  （Codexでは `codex/issue-1-add-new-feature` など）。既存の適切な作業ブランチは再利用する。
- 依頼の範囲内の実装判断は進める。依頼外の仕様拡張が必要なら、その部分の確認前に
  独立して進められる準備を済ませ、具体的な差分と判断事項を示す。
- モバイルアプリでは、環境が許し、変更内容が実機確認を要するものなら、
  iOSでは利用可能なら `zzzmisa-install-ios` を使う。他の環境ではリポジトリの検証手順に従う。

リポジトリで別のタイトル形式が指定されていない限り、Issue番号が分かっているPRの
タイトルは `Issue #<number> <summary>` にする（例: `Issue #1 音声ボタンの追加`）。
Issue番号を推測して書かない。

実際にPRを作るよう頼まれていて、GitHubツールか `gh` が使えるなら、タイトルと本文を
用意したうえで以下の権限に従ってDraft PRを作成する。本文の下書きだけならGitHubには
何も作らずMarkdownを返す。「Draft PRを作成」は実際のPR作成として扱う。

- 公開・非公開はリポジトリ指示またはGitHub APIで確認する。
- 非公開ではPR作成の明示依頼を作業ブランチのpushとDraft PR作成の許可として扱う。
- 公開ではpushはMisaが行う。ローカルの準備と本文を完成させてからpushを依頼する。
  既にpush済みなら、依頼されたPR作成を進める。
- 差分と `git status` を確認し、ユーザーの変更を自分のコミットに混ぜない。
- 同じhead/baseのPRがないか確認してから作成する。通信結果が不明なら再送前に照合する。
- 複数行の本文は構造化引数か一時ファイルに書き、`gh` では `--body-file` で渡す。

PRのマージは絶対にしない。マージはMisaが行う。
